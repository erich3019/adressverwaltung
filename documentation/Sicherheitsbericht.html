Sicherheitsbericht Adressverwaltung

Stand: 9. Oktober 2026 · Version 2.3.0 · Frontend (Next.js), Backend (ASP.NET Core OData API), nginx, Docker Compose, Hilfsskripte

1. Zusammenfassung

Der Bericht umfasst zwei Prüfungen. Die erste vom 4. Oktober 2026 ergab 18 Befunde (S-01 bis S-18): 2 kritische, 6 hohe, 5 mittlere und 5 niedrige. Die zweite vom 9. Oktober 2026 ergab 11 weitere (S-19 bis S-29): 7 mittlere und 4 niedrige, keine kritischen oder hohen.

Von den 29 Befunden sind 28 im Code behoben und am laufenden Stack überprüft. Einer ist nur im Code behoben: Das bisherige Standardpasswort des Admin-Benutzers gilt in der bestehenden Datenbank weiterhin (S-05); das ist bewusst akzeptiert.

Die zwei kritischen Befunde erlaubten den Zugriff auf alle Daten ohne Anmeldung: Jeder konnte sich über /auth/register selbst ein Konto anlegen, und die eingesetzte Next.js-Version liess sich am Seitenschutz vorbei aufrufen.

Die Adressverwaltung ist eine Demo-Anwendung ohne schützenswerte Daten. Deshalb sind zwei Punkte bewusst akzeptiert (Entscheid vom 4. Oktober 2026): die Geheimnisse in der Git-History auf GitHub und das alte Admin-Passwort in der bestehenden Datenbank. Sechs weitere Punkte bleiben als Restrisiken offen, weil sie sich nicht durch eine kleine Codeänderung lösen lassen (Abschnitt 4). Die zweite Prüfung hat einen davon erledigt (Kontosperre, vorher Teil von O-06), einen verkleinert (O-04) und einen neu aufgenommen (O-08).

2. Umfang und Vorgehen

  • Manuelle Durchsicht des Quellcodes: Controller, DbContext, Seeder, DTOs, Program.cs, lib/auth.ts, lib/api.ts, middleware.ts, Login-Formular, nginx.conf, docker-compose.yml, Dockerfiles, Skripte in scripts/ und migration/.
  • Abhängigkeiten: dotnet list package --vulnerable --include-transitive und npm audit.
  • Überprüfung der Korrekturen: 51 Backend-Integrationstests (davon 5 neu für diese Korrekturen) und Aufrufe gegen den neu gebauten Docker-Stack unter https://localhost.
  • Zweite Prüfung (9. Oktober 2026): erneute Durchsicht derselben Dateien und beider Abhängigkeitsprüfungen. Zusätzlich Aufrufe ohne Anmeldung gegen den laufenden Stack (Antwort-Header, erreichbare Endpunkte, angebotene TLS-Verfahren) und Anfragen mit unerwarteten Feldern an die OData-API über das Testprojekt. Überprüfung der Korrekturen mit 60 Tests (davon 9 neu) und am neu gebauten Stack.

Nicht Teil der Prüfung: automatisierte Penetrationstests mit externen Werkzeugen, die Inhalte der Git-History im Detail und die Infrastruktur ausserhalb des Docker-Stacks.

3. Befunde und Korrekturen

3.1 Erste Prüfung (4. Oktober 2026)

Nr.StufeBefundKorrekturStatus
S-01Kritisch Offene Registrierung: POST /auth/register war ohne Anmeldung erreichbar. Ein neu angelegtes Konto erhält ein gültiges Token und damit vollen Lese- und Schreibzugriff auf alle Adressen, Städte und Einstellungen. [Authorize] auf der Registrierung: Nur angemeldete Benutzer können weitere Benutzer anlegen. Die Tests legen ihren Benutzer direkt in der Datenbank an. Behoben
S-02Kritisch Next.js 14.2.5 mit bekannten Lücken, darunter die Umgehung der Middleware (GHSA-f82v-jwr5-mffw), die hier den gesamten Seitenschutz bildet, und Codeausführung über die Bildoptimierung (GHSA-2xp9-vwfh-vxw4). Die 14er-Linie erhält dafür keine Korrekturen mehr. Upgrade auf Next.js 15.5.27 und React 19. npm audit --omit=dev meldet keine Lücken mehr. PostCSS per overrides auf eine korrigierte Version angehoben. Behoben
S-03Hoch Geheimnisse im Repository: JWT-Schlüssel, NextAuth-Secret und Datenbankpasswort standen im Klartext in docker-compose.yml. Mit dem JWT-Schlüssel lassen sich gültige Tokens für beliebige Benutzer fälschen. Geheimnisse in die Datei .env ausgelagert (git-ignoriert, Vorlage .env.example); docker-compose.yml setzt sie als Variablen ein. Alle drei Werte neu erzeugt; das Datenbankpasswort wurde in der laufenden Datenbank geändert. Behoben (History: O-01, akzeptiert)
S-04Hoch Platzhalter-JWT-Schlüssel in appsettings.json, der ohne eigene Konfiguration stillschweigend verwendet wurde; dazu das Datenbankpasswort in derselben Datei. Schlüssel und Passwort aus appsettings.json entfernt. Das Backend startet nicht, wenn Jwt:Key fehlt, kürzer als 32 Zeichen oder der alte Platzhalter ist. Behoben
S-05Hoch Festes Standardpasswort für admin@example.com im Quellcode (DbSeeder.cs) und im README. Compose setzte kein eigenes Passwort, der Stack lief also mit diesem bekannten Zugang. Kein Standardpasswort mehr: Ohne Seed:AdminPassword erzeugt das Backend ein Zufallspasswort und schreibt es einmalig ins Log. Das gilt nur für eine leere Datenbank – in der bestehenden funktioniert das alte Passwort weiterhin (geprüft). Code behoben; Altpasswort akzeptiert (O-02)
S-06Hoch PostgreSQL (5432) und Backend (5000, ohne TLS) waren auf allen Netzwerkschnittstellen des Hosts veröffentlicht und damit am nginx vorbei erreichbar. Beide Ports nur noch an 127.0.0.1 gebunden. Aus dem Netzwerk ist ausschliesslich nginx (80/443) erreichbar. Behoben
S-07Hoch Kein Schutz gegen Passwort-Raten: Anmeldeversuche waren unbegrenzt möglich. nginx begrenzt /auth/ und /api/auth/callback/credentials auf 10 Anfragen pro Minute und Client-IP (Antwort 429). Im Test wurden 21 von 25 schnellen Versuchen abgewiesen. Behoben
S-08Hoch NuGet-Pakete mit bekannten Lücken (transitiv): Microsoft.Extensions.Caching.Memory, System.Text.Json (hoch), System.IdentityModel.Tokens.Jwt, Microsoft.IdentityModel.JsonWebTokens (mittel). Pakete aktualisiert, danach Migration auf .NET 10. Die Prüfung meldet für beide Projekte keine anfälligen Pakete. Behoben
S-09Mittel Open Redirect: Das Login-Formular leitete nach der Anmeldung ungeprüft auf den Parameter callbackUrl weiter, also auch auf fremde Seiten (Phishing über einen echten Login-Link). Nur noch Pfade innerhalb der eigenen App werden akzeptiert, alles andere führt auf die Startseite. Behoben
S-10Mittel Audit-Felder fälschbar: CreatedBy/ChangedBy wurden ersatzweise aus dem frei setzbaren Header X-User übernommen. Der Header wird nicht mehr gelesen; massgebend ist allein der Name aus dem Token. Durch einen Test abgedeckt. Behoben
S-11Mittel Benutzer-Enumeration: Der Login brauchte für unbekannte E-Mail-Adressen messbar länger (zusätzliche Hash-Berechnung), und die Registrierung antwortete für bestehende und neue Adressen unterschiedlich. Fester, einmalig berechneter Vergleichs-Hash für unbekannte Benutzer; identische Antwort der Registrierung in beiden Fällen. Behoben
S-12Mittel Backend- und Frontend-Container liefen als root. USER in beiden Dockerfiles gesetzt (Backend: app, Frontend: node). Behoben
S-13Mittel Frontend-Build ohne Lockfile: npm install holte bei jedem Build die jeweils neusten passenden Versionen, ohne Integritätsprüfung. package-lock.json versioniert, Dockerfile verwendet npm ci. Behoben
S-14Niedrig Unvollständige Sicherheitsheader; nginx gab seine Version preis. Ergänzt: Referrer-Policy, Permissions-Policy, Content-Security-Policy (frame-ancestors, base-uri, form-action, object-src); bestehende Header auch auf Fehlerantworten; server_tokens off. Behoben
S-15Niedrig Skripte create_user.sh und reset_password.sh: Eingaben wurden direkt in SQL und in Python-Quelltext eingesetzt, das Passwort am Ende im Klartext ausgegeben, Mindestlänge 6 statt 8. Werte gehen als psql-Variablen bzw. über die Umgebung; keine Passwortausgabe; Mindestlänge 8. Mit einem Passwort und Namen voller Sonderzeichen getestet. Behoben
S-16Niedrig PLZ-Suche: Ein Hochkomma in der Eingabe konnte den OData-Filter verändern (ohne Rechteausweitung). Hochkommas werden verdoppelt. Behoben
S-17Niedrig Keine Längenbegrenzung für E-Mail und Passwort bei Login und Registrierung. MaxLength 256 bzw. 128 auf den DTOs. Behoben
S-18Niedrig Ein echt wirkendes Passwort stand als «Standard» im Kommentar von migration/import_cities.py. Aus der Datei entfernt. Behoben (History: O-01, akzeptiert)

3.2 Zweite Prüfung (9. Oktober 2026)

Nr.StufeBefundKorrekturStatus
S-19Mittel Over-Posting bei POST /odata/*: Eine mitgeschickte id wurde übernommen und kollidierte später mit der Sequenz der Datenbank (Fehler 500 beim Anlegen weiterer Einträge). changedBy und changeDate liessen sich frei setzen, die Audit-Felder also fälschen. Der Schlüssel wird vor dem Speichern zurückgesetzt, die Datenbank vergibt ihn. Änderungsangaben werden beim Anlegen geleert. Durch einen Test abgedeckt. Behoben
S-20Mittel PATCH mit id im Body löste eine unbehandelte Ausnahme aus (Fehler 500). Der Schlüssel wird beim Patchen ignoriert; die übrigen Felder werden übernommen. Durch einen Test abgedeckt. Behoben
S-21Mittel OData-Fehlerantworten enthielten unter innererror den Ausnahmetyp und den Stacktrace, zum Beispiel bei $top=1000. Neuer Filter ODataErrorDetailFilter entfernt diese Angaben; die Fehlermeldung bleibt. Durch einen Test abgedeckt. Behoben
S-22Mittel Keine Kontosperre (bisher Teil von O-06): Die Begrenzung in nginx (S-07) gilt pro Client-IP. Verteilt über viele Adressen liess sich ein Passwort weiterhin unbegrenzt raten. Nach 5 Fehlversuchen ist die E-Mail-Adresse 15 Minuten gesperrt (Antwort 429), auch für das richtige Passwort. Gezählt wird ebenso für unbekannte Adressen, die Sperre verrät also nicht, welche Konten es gibt. Eine erfolgreiche Anmeldung setzt den Zähler zurück. Durch zwei Tests abgedeckt. Behoben
S-23Mittel TLS 1.2 akzeptierte schwache Verfahren wie AES256-SHA: statisches RSA ohne Forward Secrecy, CBC und SHA-1. Für TLS 1.2 nur noch ECDHE mit AES-GCM oder ChaCha20-Poly1305; Session-Tickets abgeschaltet. TLS 1.3 ist unverändert. Behoben
S-24Mittel Das Frontend-Image lief auf Node.js 20. Diese Linie erhält seit dem 30. April 2026 keine Sicherheitsupdates mehr. Umstellung aller drei Build-Stufen auf node:22-alpine. Behoben
S-25Mittel Google-Anmeldung (derzeit nicht konfiguriert): Mit gesetzten Google-Variablen hätte jedes beliebige Google-Konto eine Session erhalten und die Seiten erreicht. Daten wären nicht sichtbar gewesen, weil dieser Session das Backend-Token fehlt. NextAuth lehnt Anmeldungen ohne Backend-Token ab (Rückkehr zur Login-Seite mit Hinweis), und die Middleware lässt nur Sessions mit Backend-Token durch. Behoben
S-26Niedrig /odata und /odata/$metadata waren ohne Anmeldung lesbar und legten das Datenmodell offen. Ein neuer Controller ohne [Authorize] wäre offen gewesen. Fallback-Policy in Program.cs: Jeder Endpunkt verlangt ein gültiges Token. Einzige Ausnahme ist POST /auth/login mit [AllowAnonymous]. Durch Tests abgedeckt. Behoben
S-27Niedrig API-Antworten mit Personendaten und Tokens waren zwischenspeicherbar. Die Antworten gaben Server: Kestrel und X-Powered-By: Next.js preis. Das Backend akzeptierte jedes HMAC-Verfahren für die Token-Signatur. Cache-Control: no-store auf allen Backend-Antworten; beide Kennungen abgeschaltet; nur noch HS256 zugelassen. Behoben
S-28Niedrig Die Content-Security-Policy beschränkte nicht, woher Skripte geladen und wohin Verbindungen aufgebaut werden. Backend- und Frontend-Container liefen mit den Standard-Capabilities von Docker. CSP um default-src 'self' sowie script-src, style-src, img-src und connect-src ergänzt. Inline-Skripte bleiben erlaubt, weil Next.js sie braucht (siehe O-04). Beide Container laufen mit no-new-privileges und ohne Capabilities. Behoben
S-29Niedrig reset_password.sh prüfte die Mindestlänge nicht, wenn das Passwort als Argument übergeben wurde. create_user.sh liess dieselbe E-Mail-Adresse in anderer Gross-/Kleinschreibung ein zweites Mal zu. Die Längenprüfung gilt für beide Eingabewege. E-Mail-Adressen werden wie im Backend in Kleinbuchstaben gespeichert und ohne Rücksicht auf die Schreibweise verglichen. Behoben

4. Akzeptierte Risiken und offene Punkte

O-01 und O-02 sind für die Demo-Anwendung akzeptiert. Bei einem Einsatz mit echten Daten sind sie vor der Inbetriebnahme zu erledigen. O-03 bis O-08 sind offene Restrisiken.

Nr.PunktStand und Empfehlung
O-01 Geheimnisse in der Git-History auf GitHub: nginx/ssl/key.pem, frontend/.env.local, Postman-Vault-Key, die alten Werte aus docker-compose.yml und das Passwort aus S-18. Akzeptiert (Demo-Anwendung). JWT-Schlüssel, NextAuth-Secret und Datenbankpasswort sind dennoch bereits ersetzt. Bei einem Einsatz mit echten Daten: TLS-Zertifikat neu erzeugen und Postman-Vault-Key ersetzen. Unabhängig von der Demo-Anwendung gilt: Wird das Passwort aus S-18 an anderer Stelle verwendet, ist es dort zu ändern.
O-02 Das frühere Standardpasswort von admin@example.com gilt in der bestehenden Datenbank noch. Akzeptiert (Demo-Anwendung). Bei einem Einsatz mit echten Daten ./scripts/reset_password.sh ausführen.
O-03 OData-Listen ohne Seitengrösse: GET /odata/Cities liefert alle rund 4000 Zeilen in einer Antwort; MaxTop begrenzt nur ausdrückliche $top-Angaben. PageSize setzen. Das verlangt Blättern im Frontend, das heute die ganze Liste in einer Antwort erwartet – deshalb nicht in dieser Runde.
O-04 Das Backend-Token ist für JavaScript im Browser lesbar (session.accessToken). Eine XSS-Lücke würde es preisgeben. Im Code wurde keine solche Lücke gefunden. Seit S-28 dürfen Skripte nur vom eigenen Ursprung geladen werden und Verbindungen nur dorthin gehen; Inline-Skripte sind aber weiterhin erlaubt. Offen: API-Aufrufe über Next.js-Routen leiten, damit das Token den Server nicht verlässt, und eine strikte script-src-CSP mit Nonces einführen.
O-05 Keine Rollen: Jeder angemeldete Benutzer darf alles, auch Einstellungen ändern und Benutzer anlegen. Rolle «Admin» im Token einführen und Registrierung sowie Einstellungen darauf beschränken.
O-06 Kein Widerruf ausgestellter Tokens (8 Stunden gültig). Die Kontosperre ist seit S-22 vorhanden; ihr Zähler liegt im Arbeitsspeicher und geht bei einem Neustart des Backends verloren. Kürzere Token-Laufzeit oder Sperrliste. Die Sperre lässt sich missbrauchen, um einen Benutzer für 15 Minuten auszusperren; das ist der übliche Preis einer Kontosperre.
O-07 npm audit meldet 9 Einträge in Entwicklungswerkzeugen (7 hoch, 2 mittel; am 4. Oktober waren es 7), über Tailwind CSS 3 und ESLint. Sie laufen nur beim Build mit eigenen Dateien, nicht im ausgelieferten Frontend. Mit einer Migration auf Tailwind CSS 4 beheben.
O-08 Das Backend verbindet sich als Datenbank-Superuser postgres. Eine Lücke im Backend hätte damit Zugriff auf die ganze Datenbankinstanz. Eigene Datenbankrolle mit Rechten nur auf die Datenbank adressverwaltung. Das verlangt eine Umstellung der bestehenden Datenbank – deshalb nicht in dieser Runde.

6. Auswirkungen auf den Betrieb

  • Der Stack braucht vor dem Start die Datei .env; auf diesem Rechner ist sie mit neuen Werten angelegt.
  • Bestehende Sitzungen sind durch den neuen JWT-Schlüssel und das neue NextAuth-Secret ungültig; einmal neu anmelden.
  • Lokales dotnet run braucht Jwt__Key und ConnectionStrings__DefaultConnection aus der Umgebung (siehe README).
  • Neue Benutzer entstehen über ./scripts/create_user.sh oder durch einen angemeldeten Benutzer über /auth/register.

Seit der zweiten Prüfung gilt zusätzlich:

  • Images neu bauen (docker compose up --build -d) und nginx neu starten, damit die geänderte Konfiguration gilt. Bestehende Sitzungen bleiben gültig.
  • Nach 5 falschen Passwörtern ist eine E-Mail-Adresse 15 Minuten gesperrt. Ein Neustart des Backends hebt die Sperre auf.
  • /odata/$metadata verlangt jetzt ein Token. Werkzeuge wie Postman brauchen dafür den Authorization-Header.
  • Eine Datei von einem fremden Ursprung (Schrift, Skript, Bild, API) braucht einen passenden Eintrag in der CSP in nginx/nginx.conf, sonst blockiert der Browser sie.
  • Die Google-Anmeldung wird abgelehnt, bis das Backend für eine Google-Identität ein Token ausstellen kann.
  • Sehr alte Clients ohne ECDHE und AES-GCM können sich nicht mehr verbinden; aktuelle Browser sind nicht betroffen.
