1.1 Was wird gebaut?

In diesem Tutorial entwickeln wir gemeinsam eine vollständige Adressverwaltungs-Webapplikation mit CRUD-Funktionalität (Create, Read, Update, Delete). Die Applikation ermöglicht es, Personenadressen zu erfassen, anzuzeigen, zu bearbeiten und zu löschen. Zusätzlich bietet sie eine PLZ-Wertehilfe (Autocomplete), eine Einstellungsseite und eine vollständige Benutzerauthentifizierung mit Login.

Eine Adresse besteht aus folgenden Feldern:

1.4 Architektur-Überblick

Die Applikation besteht aus drei voneinander unabhängigen Diensten, die über Docker Compose verwaltet werden. Jeder Dienst läuft in einem eigenen Container und kommuniziert über definierte Ports:

Browser Benutzer
↔
Next.js :3000 Frontend
↔
ASP.NET Core :5000 Backend API
↔
PostgreSQL :5432 Datenbank

Die Kommunikation zwischen den Komponenten läuft so ab:

  1. Browser → Next.js (Port 3000): Der Benutzer greift über den Browser auf die Next.js-Applikation zu. Next.js rendert die Seiten (teil­weise serverseitig, teils clientseitig).
  2. Next.js → Backend (Port 5000): Für Datenbankoperationen sendet Next.js HTTP-Requests an die ASP.NET Core API. Alle Requests (ausser Login/Register) enthalten einen JWT im Authorization-Header.
  3. Backend → PostgreSQL (Port 5432): Das Backend kommuniziert via Entity Framework Core mit der PostgreSQL-Datenbank. Innerhalb von Docker nutzen sich die Dienste über Docker-interne Hostnamen (z.B. db).
Warum OData statt REST?

Eine klassische REST-API braucht separate Endpunkte für «alle Adressen», «Adressen aus Zürich», «die ersten 10 Adressen sortiert nach Name» usw. OData löst das eleganter: Ein einziger Endpunkt (/odata/Adressen) akzeptiert standardisierte Query-Parameter für Filter, Sortierung und Paging. Das spart Boilerplate-Code im Backend und gibt dem Frontend grosse Flexibilität.

Zusammenfassung Kapitel 1

  • Wir bauen eine Full-Stack-Adressverwaltung: Next.js (Frontend) + ASP.NET Core OData (Backend) + PostgreSQL (DB).
  • JWT schützt die API-Endpunkte: Nach dem Login erhält der Client ein Token, das er bei jedem Request mitsendet.
  • Docker Compose startet alle drei Dienste mit einem Befehl – reproduzierbar auf jedem Rechner.
  • OData ersetzt viele REST-Endpunkte durch einen einzigen flexiblen Abfrage-Endpunkt.

Dieser Schlüssel verschlüsselt das Session-Cookie, das den JWT enthält. Wird er geändert, werden alle aktiven Sessions ungültig. Verwende niemals «test», «geheim» oder ähnliche einfache Werte – generiere ihn mit openssl rand -base64 32.

3.2 AuditableEntity

Alle Adressen haben Audit-Felder: Wann wurde ein Datensatz erstellt, von wem, wann zuletzt geändert? Diese Felder zu jeder Entität hinzuzufügen wäre redundant (DRY-Verletzung). Stattdessen definieren wir eine abstrakte Basisklasse:

Models/AuditableEntity.cs
namespace AdressverwaltungApi.Models;

/// Basisklasse für alle Entitäten mit Audit-Felder.
/// Felder werden automatisch im DbContext.SaveChanges befüllt.
public abstract class AuditableEntity
{
    public string  CreateDate { get; set; } = string.Empty;
    public string  CreatedBy  { get; set; } = string.Empty;
    public string? ChangeDate { get; set; }
    public string? ChangedBy  { get; set; }
    public string  DateFrom   { get; set; } = string.Empty;
    public string? DateTo     { get; set; }
}

Die Befüllung erfolgt automatisch im AdresseDbContext, indem SaveChanges() und SaveChangesAsync() überschrieben werden. Dabei wird geprüft, welcher Benutzer den Request ausgeführt hat (aus dem JWT-Claim oder dem X-User-Header):

Data/AdresseDbContext.cs – ApplyAuditFields (Ausschnitt)
private void ApplyAuditFields()
{
    var now         = DateTime.UtcNow.ToString("o");
    var currentUser = GetCurrentUser(); // aus JWT-Claim oder X-User-Header

    foreach (var entry in ChangeTracker.Entries<AuditableEntity>())
    {
        if (entry.State == EntityState.Added)
        {
            entry.Entity.CreateDate = now;
            entry.Entity.CreatedBy  = currentUser;
            entry.Entity.DateFrom   = now;
        }
        if (entry.State == EntityState.Modified)
        {
            entry.Entity.ChangeDate = now;
            entry.Entity.ChangedBy  = currentUser;
        }
    }
}

public override int SaveChanges()
{
    ApplyAuditFields();
    return base.SaveChanges();
}

public override Task<int> SaveChangesAsync(
    CancellationToken cancellationToken = default)
{
    ApplyAuditFields();
    return base.SaveChangesAsync(cancellationToken);
}
Warum beide SaveChanges überschreiben?

EF Core bietet zwei Varianten: den synchronen SaveChanges() und den asynchronen SaveChangesAsync(). Beide müssen ApplyAuditFields() aufrufen – sonst werden Audit-Felder bei asynchronen Operationen nicht gesetzt. Dieser Fehler ist schwer zu finden, weil er je nach Aufrufkontext auftritt.

3.3 AdresseDbContext

Der AdresseDbContext ist die zentrale Klasse für den Datenbankzugriff. Er kennt alle Tabellen, konfiguriert die Spaltennamen und befüllt die Audit-Felder automatisch:

Data/AdresseDbContext.cs (Ausschnitt)
public class AdresseDbContext : DbContext
{
    private readonly IHttpContextAccessor? _httpContextAccessor;

    public AdresseDbContext(
        DbContextOptions<AdresseDbContext> options,
        IHttpContextAccessor? httpContextAccessor = null)
        : base(options)
    {
        _httpContextAccessor = httpContextAccessor;
    }

    public DbSet<Adresse>  Adressen { get; set; } = null!;
    public DbSet<City>     Cities   { get; set; } = null!;
    public DbSet<User>     Users    { get; set; } = null!;
    public DbSet<Settings> Settings { get; set; } = null!;

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // Alle string-Felder auf case-insensitive Collation setzen
        modelBuilder.UseCollation("case_insensitive");

        // City: zusammengesetzter Index für schnelle PLZ-Suche
        modelBuilder.Entity<City>()
            .HasIndex(c => c.PostalCode)
            .HasDatabaseName("IX_Cities_PostalCode");
    }

    private string GetCurrentUser()
    {
        var claim  = _httpContextAccessor?.HttpContext?.User?.Identity?.Name;
        var header = _httpContextAccessor?.HttpContext?.Request.Headers["X-User"]
                         .FirstOrDefault();
        return !string.IsNullOrWhiteSpace(claim)  ? claim
             : !string.IsNullOrWhiteSpace(header) ? header
             : "system";
    }
}

3.4 DbSeeder

Beim ersten Start der Applikation muss mindestens ein Admin-Benutzer existieren, damit man sich einloggen kann. Diese Aufgabe übernimmt DbSeeder — eine statische Hilfsklasse, die nach dem Datenbank-Setup aufgerufen wird.

Clean Code: SRP (Single Responsibility Principle)

Program.cs ist für Konfiguration und Middleware zuständig — nicht für das Erstellen von Testdaten. Deshalb wurde die Seed-Logik in eine eigene Klasse DbSeeder.cs ausgelagert. Jede Klasse hat nur eine Aufgabe.

Data/DbSeeder.cs
public static class DbSeeder
{
    public static void Seed(
        AdresseDbContext      db,
        IPasswordHasher<User> hasher,
        IConfiguration        config)
    {
        // Bereits Benutzer vorhanden? Nicht nochmal seeden.
        if (db.Users.Any()) return;

        // Zugangsdaten aus appsettings.Development.json lesen
        var email    = config["Seed:AdminEmail"]    ?? "[email protected]";
        var password = config["Seed:AdminPassword"] ?? "Test-1234!";

        var admin = new User
        {
            Email       = email,
            DisplayName = "Admin",
        };
        admin.PasswordHash = hasher.HashPassword(admin, password);

        db.Users.Add(admin);
        db.SaveChanges();
    }
}

In Program.cs wird der Seeder nach dem Starten der App aufgerufen:

Program.cs – DbSeeder-Aufruf
// Datenbank erstellen und Seed-Daten einfügen
using var scope = app.Services.CreateScope();
var db     = scope.ServiceProvider.GetRequiredService<AdresseDbContext>();
var hasher = scope.ServiceProvider.GetRequiredService<IPasswordHasher<User>>();
db.Database.EnsureCreated();
DbSeeder.Seed(db, hasher, app.Configuration);

3.5 EF Core: EnsureCreated vs. Migrations

Entity Framework Core bietet zwei Wege, die Datenbankstruktur zu erstellen:

MethodeWas sie tutWann einsetzen?
EnsureCreated() Erstellt die Datenbank und alle Tabellen, falls sie noch nicht existieren. Führt keine Migrations aus. Lernprojekte, Docker-Umgebungen, wo die DB bei jedem Start frisch erstellt wird.
Migrations (dotnet ef migrate) Erstellt Migrationsskripte für jede Schemaänderung. Ältere Daten bleiben erhalten. Produktivumgebungen, wo die DB Daten enthält, die nicht verloren gehen dürfen.
EnsureCreated + Migrations = Konflikt!

Wenn EnsureCreated() aufgerufen wurde, kann dotnet ef database update Migrations nicht anwenden, weil EF Core keine Migrations-History-Tabelle kennt. In Docker ist das kein Problem, weil bei docker compose down -v das Volume gelöscht und die DB neu erstellt wird. Für Produktivumgebungen immer Migrations verwenden.

OData (Open Data Protocol) ist ein REST-basiertes Protokoll, das standardisierte URL-Parameter für Abfragen definiert. Das Backend muss keine eigenen Filterendpunkte implementieren — OData übersetzt die URL-Parameter automatisch in SQL-Abfragen.

4.3 Generischer ODataCrudController<T>

Ohne Basisklasse würden AdressenController und CitiesController nahezu identischen Code enthalten: GET, POST, PATCH, DELETE — jedes Mal dieselbe Struktur, nur der Typ verschieden. Das verletzt das DRY-Prinzip (Don't Repeat Yourself).

Die Lösung: eine abstrakte generische Basisklasse, die die gesamte CRUD-Logik einmal implementiert. Abgeleitete Controller müssen nur noch die Entity-spezifischen Teile definieren:

Controllers/ODataCrudController.cs
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.OData.Routing.Controllers;
using Microsoft.EntityFrameworkCore;

namespace AdressverwaltungApi.Controllers;

[Authorize]  // Alle abgeleiteten Controller sind automatisch geschützt!
public abstract class ODataCrudController<TEntity> : ODataController
    where TEntity : class
{
    protected readonly AdresseDbContext _context;
    protected readonly ILogger _logger;

    protected ODataCrudController(AdresseDbContext context, ILogger logger)
    {
        _context = context;
        _logger  = logger;
    }

    // Abgeleitete Controller definieren, welches DbSet verwendet wird
    protected abstract DbSet<TEntity> Entities { get; }
    protected abstract string EntityDisplayName { get; }

    // GET /odata/{EntitySet}
    [HttpGet]
    [EnableQuery]
    public virtual IActionResult Get() =>
        Ok(_context.Set<TEntity>().AsNoTracking());

    // GET /odata/{EntitySet}(5)
    [HttpGet("{key}")]
    [EnableQuery]
    public virtual async Task<IActionResult> GetById([FromRoute] int key)
    {
        var entity = await Entities.FindAsync(key);
        if (entity is null)
            return NotFound($"{EntityDisplayName} mit Id {key} nicht gefunden.");
        return Ok(entity);
    }

    // POST /odata/{EntitySet}
    [HttpPost]
    public virtual async Task<IActionResult> Post([FromBody] TEntity entity)
    {
        if (!ModelState.IsValid) return BadRequest(ModelState);
        Entities.Add(entity);
        await _context.SaveChangesAsync();
        return Created(entity);
    }

    // PATCH /odata/{EntitySet}(5)
    [HttpPatch("{key}")]
    public virtual async Task<IActionResult> Patch(
        [FromRoute] int key, [FromBody] Delta<TEntity> delta)
    {
        if (!ModelState.IsValid) return BadRequest(ModelState);
        var entity = await Entities.FindAsync(key);
        if (entity is null) return NotFound();
        delta.Patch(entity);
        if (!TryValidateModel(entity)) return BadRequest(ModelState);
        await _context.SaveChangesAsync();
        return Updated(entity);
    }

    // DELETE /odata/{EntitySet}(5)
    [HttpDelete("{key}")]
    public virtual async Task<IActionResult> Delete([FromRoute] int key)
    {
        var entity = await Entities.FindAsync(key);
        if (entity is null) return NotFound();
        Entities.Remove(entity);
        await _context.SaveChangesAsync();
        return NoContent();
    }
}

public async Task<IActionResult> Register([FromBody] RegisterRequest req)

    if (await _db.Users.AnyAsync(u =>

[HttpPost("login")]
public async Task<IActionResult> Login([FromBody] LoginRequest req)
{
    var user = await _db.Users.FirstOrDefaultAsync(u =>
        u.Email.ToUpperInvariant() == req.Email.ToUpperInvariant());

    // TIMING-ATTACK-SCHUTZ: Passwort immer prüfen (auch bei unbekanntem User)
    var hashZuPruefen = user?.PasswordHash ?? "dummy-hash";
    var result = _hasher.VerifyHashedPassword(null!, hashZuPruefen, req.Password);

    if (user == null || result == PasswordVerificationResult.Failed)
        return Unauthorized(new { message = "Ungültige Anmeldedaten." });

    return Ok(new LoginResponse(
        Id:    user.Id.ToString(),
        Name:  user.DisplayName,
        Email: user.Email,
        Token: GenerateJwt(user)   // ← JWT ausstellen (siehe Kap. 5.4)
    ));
}
Was ist ein Timing-Angriff?

Ein Angreifer misst die Antwortzeit der API. Wenn «E-Mail unbekannt» schneller antwortet als «falsches Passwort» (weil das Hashing übersprungen wird), kann er daraus schliessen, welche E-Mail-Adressen existieren. Wir verhindern das, indem wir das Passwort immer prüfen – auch wenn der Benutzer nicht gefunden wurde. Der Dummy-Hash stellt sicher, dass die Antwortzeit gleich lang ist.

5. JWT – JSON Web Token NEU v2.1

5.1 Was ist ein JWT?

Ein JSON Web Token (JWT) ist ein offener Standard (RFC 7519), der eine kompakte und selbst­enthaltene Methode definiert, um Informationen als JSON-Objekt sicher zwischen zwei Parteien zu übertragen. Im Gegensatz zu einer klassischen Server-Session werden beim JWT alle sitzungsrelevanten Daten im Token selbst gespeichert – der Server muss keine Session-Tabelle führen.

Ein JWT besteht aus drei Base64url-kodierten Teilen, die durch einen Punkt . getrennt sind:

Header.Payload.Signatur
JWT-Bestandteile im Überblick
TeilInhalt (Beispiel)Zweck
Header { "alg": "HS256", "typ": "JWT" } Algorithmus & Token-Typ
Payload { "sub": "42", "email": "[email protected]", "role": "Admin", "exp": 1735689600 } Nutzdaten (Claims)
Signatur HMACSHA256(base64(header)+"."+base64(payload), secret) Integritätsprüfung

Standard-Claims im Payload

Der Payload enthält sogenannte Claims – Schlüssel-Wert-Paare mit Informationen über den Benutzer oder den Token selbst. Wichtige reservierte Claims:

  • sub – Subject (z. B. User-ID)
  • iss – Issuer (ausstellende Instanz)
  • aud – Audience (Empfänger)
  • exp – Expiration Time (Unix-Timestamp)
  • iat – Issued At (Ausstellungszeitpunkt)
  • jti – JWT ID (eindeutige Token-ID)
Hinweis: Der Payload ist Base64url-kodiert, aber nicht verschlüsselt. Jeder kann den Inhalt lesen (z. B. mit jwt.io). Sensible Daten (Passwörter, Kreditkartennummern) gehören nie in einen JWT.

5.2 Warum JWT?

Traditionelle Web-Applikationen nutzen Server-seitige Sessions: Nach dem Login legt der Server eine Session-Einheit an und gibt dem Client eine Session-ID (Cookie). Bei jeder Anfrage schlägt der Server die Session in einer Datenbank oder einem In-Memory-Store nach. Dieses Modell hat Nachteile beim horizontalen Skalieren: Alle Server-Instanzen müssen denselben Session-Store lesen.

JWT verlagert den Zustand vollständig in den Token. Der Server muss nichts speichern; er prüft nur die Signatur. Damit ist JWT für folgende Szenarien besonders geeignet:

Session-Cookie vs. JWT
MerkmalSession-CookieJWT
Zustand auf ServerJa (Session-Store)Nein (stateless)
SkalierbarkeitShared Session-Store nötigJeder Server kann validieren
Payload lesbarNein (opaque ID)Ja (Base64url)
Ablauf steuerbarSession-Timeoutexp-Claim
Token widerrufenServer-seitig sofortErst nach Ablauf (ohne Blocklist)
MicroservicesUmständlichIdeal (jeder Service prüft selbst)

In unserer Adressverwaltungs-WebApp verwenden wir JWT weil:

  • das Backend (ASP.NET Core) und das Frontend (Next.js) auf unterschiedlichen Ports laufen,
  • CORS-Anfragen einfacher per Authorization: Bearer … Header funktionieren als per Cookie,
  • NextAuth.js das JWT nativ in seiner Session verwalten kann.

var keyBytes   = Encoding.UTF8.GetBytes(jwtSection["Key"]!);

builder.Services.AddAuthentication(options =>
{
    options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme    = JwtBearerDefaults.AuthenticationScheme;
})
.AddJwtBearer(options =>
{
    options.TokenValidationParameters = new TokenValidationParameters
    {
        ValidateIssuerSigningKey = true,
        IssuerSigningKey         = new SymmetricSecurityKey(keyBytes),
        ValidateIssuer           = true,
        ValidIssuer              = jwtSection["Issuer"],
        ValidateAudience         = true,
        ValidAudience            = jwtSection["Audience"],
        ValidateLifetime         = true,
        ClockSkew                = TimeSpan.Zero   // keine Toleranz beim Ablauf
    };
});

var app = builder.Build();

// Middleware-Reihenfolge ist kritisch!

5.4 JWT ausstellen – GenerateJwt()

Beim erfolgreichen Login ruft der AuthController die Hilfsmethode GenerateJwt() auf. Diese erstellt das Token mit den Claims des Benutzers:

backend/Controllers/AuthController.cs – GenerateJwt()
private string GenerateJwt(User user)
{
    var jwtSection = _config.GetSection("Jwt");
    var keyBytes   = Encoding.UTF8.GetBytes(jwtSection["Key"]!);
    var creds      = new SigningCredentials(
                         new SymmetricSecurityKey(keyBytes),
                         SecurityAlgorithms.HmacSha256);

    var claims = new[]
    {
        new Claim(JwtRegisteredClaimNames.Sub,   user.Id.ToString()),
        new Claim(JwtRegisteredClaimNames.Email,  user.Email),
        new Claim(JwtRegisteredClaimNames.Jti,    Guid.NewGuid().ToString()),
        new Claim(ClaimTypes.Role,                user.Role ?? "User")
    };

    var token = new JwtSecurityToken(
        issuer:             jwtSection["Issuer"],
        audience:           jwtSection["Audience"],
        claims:             claims,
        expires:            DateTime.UtcNow.AddMinutes(
                                double.Parse(jwtSection["ExpiresInMinutes"]!)),
        signingCredentials: creds);

    return new JwtSecurityTokenHandler().WriteToken(token);
}

// Verwendung im Login-Endpunkt:
[HttpPost("login")]
public async Task<IActionResult> Login(LoginDto dto)
{
    var user = await _context.Users
        .FirstOrDefaultAsync(u => u.Email == dto.Email);

    if (user == null || !BCrypt.Net.BCrypt.Verify(dto.Password, user.PasswordHash))
        return Unauthorized(new { message = "Ungültige Anmeldedaten" });

    var jwt = GenerateJwt(user);
    return Ok(new { token = jwt, email = user.Email, role = user.Role });
}

Das Next.js Frontend verwendet NextAuth.js als Authentifizierungsschicht. NextAuth speichert das vom Backend erhaltene JWT in seiner eigenen verschlüsselten Session (JWE-Cookie). Damit das möglich ist, müssen die TypeScript-Typen erweitert und die JWT/Session-Callbacks konfiguriert werden.

Typen erweitern – next-auth.d.ts

auth.ts – JWT- und Session-Callback

frontend/auth.ts
import NextAuth from "next-auth";
import CredentialsProvider from "next-auth/providers/credentials";

export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [
    CredentialsProvider({
      name: "Credentials",
      credentials: {
        email:    { label: "E-Mail",    type: "email" },
        password: { label: "Passwort", type: "password" },
      },
      async authorize(credentials) {
        const res = await fetch(
          `${process.env.BACKEND_URL}/api/auth/login`,
          {
            method: "POST",
            headers: { "Content-Type": "application/json" },
            body: JSON.stringify(credentials),
          }
        );
        if (!res.ok) return null;
        const data = await res.json();
        // data = { token, email, role }
        return { id: data.email, email: data.email,
                 token: data.token, role: data.role };
      },
    }),
  ],

  callbacks: {
    // 1. JWT-Callback: Backend-Token in NextAuth-JWT eintragen
    async jwt({ token, user }) {
      if (user) {
        token.accessToken = (user as any).token;
        token.role        = (user as any).role;
      }
      return token;
    },
    // 2. Session-Callback: NextAuth-JWT in die Session übertragen
    async session({ session, token }) {
      session.accessToken    = token.accessToken as string;
      session.user.role      = token.role as string;
      return session;
    },
  },

  pages: { signIn: "/login" },
  session: { strategy: "jwt" },
});

  return fetch(`${process.env.BACKEND_URL}${path}`, {
    ...options,
    headers: {
      "Content-Type": "application/json",
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...options.headers,
    },
  });
}

5.7 Ablauf: Login bis API-Aufruf

Das folgende Ablaufdiagramm zeigt, was passiert, wenn ein Benutzer sich anmeldet und danach eine geschützte Ressource abruft. Die 9 Schritte verteilen sich auf drei Parteien: Browser, Next.js Server und ASP.NET Core Backend.

1
Benutzer gibt Credentials ein – Das Login-Formular (/login) sendet E-Mail und Passwort via signIn("credentials", …).
2
NextAuth ruft authorize() auf – Dieser Callback sendet einen POST /api/auth/login an das ASP.NET Backend.
3
Backend prüft Credentials – BCrypt-Vergleich des Passwort-Hashes. Bei Erfolg wird GenerateJwt(user) aufgerufen.
4
Backend antwortet mit JWT – { "token": "eyJ…", "email": "…", "role": "Admin" }
5
NextAuth JWT-Callback – Das Backend-Token wird in token.accessToken gespeichert und in einem verschlüsselten Session-Cookie abgelegt.
6
Browser erhält Session-Cookie – Alle nachfolgenden Next.js-Anfragen sind automatisch authentifiziert.
7
Server Component ruft apiFetch() auf – Die Funktion liest die Session, extrahiert accessToken und setzt den Authorization: Bearer …-Header.
8
Backend validiert JWT – Die JWT-Middleware prüft Signatur, Aussteller, Audience und Ablaufzeit. Bei Erfolg wird der Controller aufgerufen.
9
Daten fliessen zurück – Das Backend antwortet mit den angeforderten OData-Daten. Next.js rendert die Seite und zeigt sie dem Benutzer.
Sicherheitsaspekt – Token-Ablauf: Das JWT läuft nach 60 Minuten ab (ExpiresInMinutes: 60). In der aktuellen Implementierung wird der Benutzer danach beim nächsten API-Aufruf automatisch abgemeldet. Eine Token-Erneuerung («Refresh Token») ist nicht implementiert, wäre aber der nächste Schritt für Produktionsumgebungen.

import { auth } from "@/auth";

}

A.2 Das Import-Skript

scripts/import_cities.py
#!/usr/bin/env python3
"""
import_cities.py – PLZ-Daten aus AMTOVZ_CSV_LV95.csv in PostgreSQL importieren.

Verwendung:
    python3 import_cities.py --csv AMTOVZ_CSV_LV95.csv --dsn "postgresql://adressuser:adresspass@localhost:5432/adressdb"

Voraussetzungen:
    pip install psycopg2-binary
"""

import argparse
import csv
import sys
import psycopg2

# ---- Argument-Parsing ----
parser = argparse.ArgumentParser(description="PLZ-Import aus swisstopo CSV")
parser.add_argument("--csv",  required=True, help="Pfad zur CSV-Datei")
parser.add_argument("--dsn",  required=True, help="PostgreSQL-DSN")
parser.add_argument("--dry-run", action="store_true",
                    help="Nur einlesen, nichts in die DB schreiben")
args = parser.parse_args()

# ---- CSV einlesen ----
print(f"Lese {args.csv} …")
seen   = set()    # (PLZ4, Ortschaftsname) – Duplikate vermeiden
cities = []

with open(args.csv, encoding="utf-8-sig", newline="") as f:
    reader = csv.DictReader(f, delimiter=";")
    for row in reader:
        plz  = row["PLZ4"].strip()
        name = row["Ortschaftsname"].strip()
        key  = (plz, name)
        if key in seen:
            continue                # Duplikat überspringen
        seen.add(key)
        cities.append({"plz": plz, "name": name})

print(f"{len(cities)} eindeutige PLZ-Ortschaft-Kombinationen gefunden.")

if args.dry_run:
    print("Dry-run – keine Datenbankänderungen.")
    sys.exit(0)

# ---- In Datenbank schreiben ----
print("Verbinde mit Datenbank …")
conn = psycopg2.connect(args.dsn)
cur  = conn.cursor()

# Sicherstellen, dass die Tabelle existiert (EF Core hat sie bereits angelegt)
cur.execute("""
    CREATE TABLE IF NOT EXISTS "Cities" (
        "Id"        SERIAL PRIMARY KEY,
        "Plz"       VARCHAR(10) NOT NULL,
        "Name"      VARCHAR(200) NOT NULL,
        "CreatedAt" TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT NOW(),
        "UpdatedAt" TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT NOW()
    );
""")

# Bestehende Daten löschen (sauberer Neuimport)
cur.execute('DELETE FROM "Cities";')
print("Bestehende Daten gelöscht.")

# Batch-Insert
batch_size = 500
inserted   = 0
for i in range(0, len(cities), batch_size):
    batch = cities[i : i + batch_size]
    args_str = ",".join(
        cur.mogrify("(%s, %s, NOW(), NOW())", (c["plz"], c["name"])).decode()
        for c in batch
    )
    cur.execute(
        f'INSERT INTO "Cities" ("Plz","Name","CreatedAt","UpdatedAt") VALUES {args_str}'
    )
    inserted += len(batch)
    print(f"  {inserted}/{len(cities)} importiert …")

conn.commit()
cur.close()
conn.close()
print(f"Fertig! {inserted} Eintraege in die Tabelle Cities geschrieben.")

Docker-Variante: Wenn PostgreSQL in Docker läuft, muss der Port freigegeben sein: docker compose up -d db (Port 5432:5432 in docker-compose.yml). Der DSN-Hostname ist dann localhost (vom Hostsystem aus), aber db innerhalb der Docker-Netzwerks.
